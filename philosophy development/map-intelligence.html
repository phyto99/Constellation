Architectural Layer — Map × Student × Bot
Map Intelligence — Topology, Strategy Patterns & Bot Calibration
The map is not just a config parameter. It is a structured environment with known optimal strategies, observable human pattern distributions, and the ability to be configured to maximally develop any specific student. This document defines what the system needs to know about maps and how to use that knowledge.

Section 1
The Map as a Structured Variable

Currently, map_idx is a single integer in the config vector — treated identically to round_length_s or steals. The system knows it used map 3, but knows nothing about map 3. This is the same as a chess engine that records which board was used but doesn't know the rules vary by board.

A map is a structured environment with topological properties that determine which cognitive modes are favored, which human strategies emerge, and which bot behaviors produce the most informative sessions. The compiler must understand this to select the right map for a given student's development target.

The current blind spot: a student with high QTY Elo placed on a map where quantity play is impossible gets a contaminated signal — the outcome reflects map topology, not cognitive skill. The system currently cannot distinguish these.

The resolution requires three layers: a topology registry (what is each map), a strategy pattern library (what humans do on each map), and a bot calibration system (how to create the maximally informative opponent for each student-map combination).

Section 2
Map Topology Registry — What the System Needs to Know

Every map needs a topology record. This is not derived from play data — it is structural, derivable from the map definition itself. Some properties can be computed algorithmically; others require manual annotation.

Symmetry Class
Rotationally symmetric, bilaterally symmetric, or asymmetric. Symmetric maps make QTY/SPT strategies predictable across player positions. Asymmetric maps favor positional reasoning and force role differentiation.
HQ Geometry
How far are HQs from each other, from the map center, and from neutral resource clusters? Short HQ distance favors FORTRESS play. Long HQ distance favors SPT/distance-seeking strategies.
Resource Density
How many capturable positions exist, and how clustered or dispersed are they? High-density maps favor QTY (capture everything). Sparse maps force selective sequencing and spatial planning.
Chokepoint Count
How many bottleneck positions exist where territory control is decisive? High chokepoint maps reward spatial occupation and position holding. Low chokepoint maps reward open maneuvering.
Mode Affinity Vector
A [6]-dim vector over [QTY, SPT, FRT, DST, WRM, INV] rating how much each mode's scoring strategy is viable on this map. Example: a tight, HQ-centric map: [0.4, 0.6, 0.9, 0.3, 0.5, 0.7]. Used by compiler to select maps that match the target mode.
Opening Divergence
Do most players open similarly, or do opening moves diverge widely? Low-divergence maps have a dominant first move (easy to identify; tests whether students find it). High-divergence maps produce more varied data per session.
Theoretical Optimal
The provably or empirically best strategy for each mode on this map. Derived from top-percentile sessions or from simulation. Used as the THEORETICIAN bot's playbook and as the baseline for measuring student gap.
Difficulty Rating per Mode
How much does this map add to cognitive load for each mode? A map where QTY is easy (many close clusters) vs where QTY is hard (resources dispersed) should affect Elo weighting differently. NOT YET ASSERTED — needs empirical data from Phase 1.

The topology record is stored as a static JSON file (maps/topology.json), updated when new maps are added, and loaded by the compiler at session generation time. It does not go in the Ledger — it is environmental metadata, not an observation.

// maps/topology.json — structure { "0": { "name": "Map Alpha", "symmetry": "bilateral", "hq_distance_norm": 0.72, // 0=adjacent 1=opposite corners "resource_density": 0.61, // 0=sparse 1=saturated "chokepoints": 3, "mode_affinity": [0.7, 0.5, 0.8, 0.4, 0.5, 0.6], // [qty,spt,frt,dst,wrm,inv] "opening_divergence": 0.4, // 0=everyone plays the same, 1=fully random "theoretical_optimal": { "qty": [...], "spt": [...] }, "difficulty": { "qty": 0.45, "spt": 0.65, "frt": 0.30 } } }
Section 3
Strategy Pattern Library — What Humans Actually Do

Beyond the topology, the system needs to know what human players actually do when placed on each map. This is empirical knowledge accumulated from the Ledger — not derivable from the map structure alone.

The pattern library serves two purposes: it tells the compiler what this student's behavior on this map looks like vs. what most students do, and it gives the bot calibration system enough context to create a bot that plays against the student's specific tendencies — not just against generic play.

Pattern DimensionWhat it measuresHow it's capturedHow it's used
First-move distribution Where do most players send their first piece on this map? What % claim the central resource vs. the HQ-adjacent resource vs. the far edge? Round 1, move 1 position from Ledger records. Aggregated across all sessions on map_idx=X. Bot can be configured to either play the statistically dominant first move (THEORETICIAN) or to counter the student's documented first move (CONTESTER).
Phase distribution How does the average player's board position evolve round-by-round? Do most players expand in early rounds and consolidate later, or hold and then push? round_snapshots from Ledger → per-round rank_pct curves, averaged across all students on this map. Identifies the typical tempo of the map. A student who is significantly ahead or behind the average tempo curve at round 3 is showing map-specific tempo skill or deficit.
Common archetypes On this map, what strategic archetypes emerge? e.g. "Rusher" (early all-in expansion), "Turtler" (consolidate own territory), "HQ Sniper" (ignore resources, target opponent HQ), "Opportunist" (react to opponent moves). Session-level behavioral signals: early_expansion_rate, hq_attack_frequency, contested_zone_entry, reactive_vs_proactive_ratio. Student gets tagged with their dominant archetype on each map. The bot is selected to counter or mirror that archetype depending on the development target.
Student map fingerprint For a specific student: how does their play on map X differ from their play overall? Do they default to the same strategy regardless of map, or do they adapt? Compare per-map behavioral signals to student's overall mean. High deviation = map-aware player. Low deviation = map-blind player (applies same strategy everywhere). Map-blind players need maps that punish their default strategy. Map-aware players need more complex maps that force higher-order adaptation. Compiler uses this signal in map selection.
Chokepoint behavior When a chokepoint is available, what % of players take it vs. bypass it? How long do players who take chokepoints hold them? Requires positional data in Ledger (currently not stored — needs round_snapshots to include position data). FUTURE Identifies whether students understand positional leverage. A student who consistently bypasses high-value chokepoints is showing SPT deficit on positional maps.

Privacy note: Pattern data is aggregated at the cohort level before being used in compiler decisions. The system does not expose "what most students do" to students — only to the admin panel and to bot calibration. The pattern library is a system resource, not a student-facing feature.

Section 4
Bot Strategy Profiles — Six Personalities for Maximum Development

The current system treats bot configuration as a single parameter: bot_aggression (0–100). This is a scalar on a behavior that needs to be a vector. Aggression is one dimension of bot strategy. The others are: target selection logic, tempo, and adaptive vs. fixed behavior.

The following six profiles cover the full space of what a bot can do to develop a specific student. Each is defined by its development target — the cognitive dimension in the student it is designed to stress-test.

MIRROR
Target: self-model accuracy
The bot replicates the student's dominant strategy from their Ledger history. If the student always starts with a northern expansion, the bot opens with a northern expansion. The student is playing against a projection of themselves.
Deploy when: student has a strong, consistent strategy and the question is whether that strategy is fundamentally sound or exploitable. The student must either defeat their own strategy (validating its weaknesses) or watch it beat them (validating its strength).
Signal: rank_pct vs. own historical baseline on this map. If the MIRROR bot beats the student more often than the student beats the bot, the strategy has an exploitable weakness.
CONTESTER
Target: adaptability under pressure
The bot specifically targets and contests the zones the student is developing — not the strategically optimal zones. If the student typically develops the right side of the map, the bot occupies and defends the right side, forcing the student to develop somewhere they don't usually go.
Deploy when: student is map-blind (plays the same opening regardless of map) or shows low variance in strategy. The contester forces variation — the student cannot execute their default plan.
Signal: strategy_shift_speed, alternative_axis_discovery. Students who find new approaches quickly are showing genuine adaptability. Students who keep trying the same approach are showing rigidity.
ACCELERANT
Target: tempo and decision speed
The bot plays at maximum aggression in early rounds — claiming as many positions as possible as fast as possible. By round 3, the board state is already contested. The student must respond at a tempo faster than they are comfortable with.
Deploy when: student shows slow early development (round 1–2 rank_pct below average) or high move_pool_rate unused. Also ideal for students who play well when they set the pace but struggle when the opponent dictates tempo.
Signal: early_response_latency, round_1_rank_pct. Students who adapt and match the accelerant's pace are showing temporal flexibility.
TURTLER
Target: initiative and aggression
The bot plays defensively — consolidating a small territory and holding it, rather than expanding. The student must be the aggressor. There is no external pressure forcing action; the student must generate their own momentum.
Deploy when: student is reactive (low proactive_vs_reactive ratio) or when prior sessions show high variance that might be due to external pressure masking underlying skill. The turtler removes external forcing and exposes the student's natural tempo.
Signal: proactive_expansion_rate, initiative_score. A student who expands effectively against a turtler is showing self-generated strategic momentum.
THEORETICIAN
Target: skill ceiling measurement
The bot plays the theoretical optimal strategy for this map and mode, derived from the strategy pattern library. It is not adaptive — it executes the best known fixed strategy. The gap between the student's performance and the theoretician's performance IS the map-specific skill gap.
Deploy when: the student has high session count on this map (≥ 6 sessions) and the compiler needs a clean skill ceiling measurement. Not for early sessions — the student needs enough exposure that the comparison is meaningful.
Signal: rank_pct vs. theoretician is the map-mode skill gap signal. Used in Phase 2 BT transfer calculations.
ADAPTOR
Target: meta-cognitive flexibility
The bot changes strategy mid-session based on what the student is doing. If the student is expanding north, the bot shifts to contest north. If the student shifts south, the bot follows. The student is not playing against a fixed strategy — they are playing against an opponent who is reading them in real time.
Deploy when: student has high experience on this map and simple strategies no longer produce information. The adaptor tests whether the student can reason about an opponent who is reasoning about them — the highest-order spatial cognition available in this game.
Signal: counter_detection_speed, strategy_oscillation. The student who recognizes the adaptor is adapting and responds with deception (decoy expansion) is showing meta-game reasoning.
Section 5
The Perfect Session — Composing Student × Map × Bot

The compiler's current job is: select mode → build config vector. The future compiler's job is: select mode → select map that best exposes that mode → select bot strategy that maximally develops the student on that map in that mode. Three decisions, not one.

The composition principle: the best session is the one that maximizes expected KL divergence between the student's prior model and their posterior model after the session. Every component choice (map, bot type, config parameters) is an instrument for moving the student's cognitive model.

Student ProfileTarget ModeMap Selection LogicBot ProfileWhy
Zero-session student QTY (calibration) High-resource-density, symmetric, low chokepoints — minimum environmental complexity TURTLER at aggression=30 Let the student explore freely. Turtler removes pressure. Symmetric map removes positional confusion. Clean baseline capture.
Map-blind student (same opening always) Any deficit mode Asymmetric map that makes their default opening suboptimal CONTESTER The map itself provides structural pressure against their default strategy. The contester adds behavioral pressure. Student must adapt twice.
High QTY, low SPT SPT High-chokepoint, sparse-resource map — positional leverage is the main instrument THEORETICIAN (SPT optimal) Student's quantity instinct is useless on this map. The theoretician shows what optimal SPT play looks like. The gap is the SPT deficit signal.
High-variance student (inconsistent performance) Student's strongest mode Their highest-frequency map (most familiar environment) TURTLER Remove all external forcing. Familiar map, passive opponent. Variance in this condition = psychological inconsistency, not skill inconsistency. Clean diagnosis.
Expert student (high Elo, low velocity) Any mode Novel map (low map_idx history) — unfamiliar topology ADAPTOR Expert has mastered all familiar maps. New map breaks their cached strategies. Adaptor forces them to reason meta-cognitively. Maximum KL gain available.
RADICAL zone student (compiler targets deficit) Deficit mode Map with HIGH affinity for the deficit mode — maximum exposure to what they're weak at MIRROR (their dominant mode strategy, now wrong context) Student enters their strongest strategy into a mode that doesn't reward it, AND plays against a bot that does exactly what they do. Double displacement: mode is wrong, strategy is mirrored.

The composition table above is a heuristic framework. The real compiler should eventually optimize this directly by minimizing the expected entropy of the student's posterior model — which requires fitted parameters (Phase 3). Until then, the table gives deterministic, principled choices that are better than the current single-axis optimization.

Section 6
What the Ledger Needs — New Signals for Map Intelligence

The current Ledger records outcome and config vector. Map intelligence requires behavioral signals that go into the session record. These are observed quantities — they go in the Ledger as part of the session observation, not as derived views.

// New fields in session observation (appended to existing record) "map_signals": { "bot_profile": "CONTESTER", // which bot strategy was used "opening_position": [x, y], // first move target position "archetype_tag": "rusher", // inferred from behavioral signals "strategy_shift_count": 2, // how many times student changed approach "chokepoint_claim_rate": 0.67, // fraction of available chokepoints claimed "early_rank_pct": 0.42, // rank at round floor(rounds/3) "tempo_delta": -0.15, // student tempo vs map average (neg=slower) "map_affinity_match": 0.78 // how well this map matched the target mode }

Section 7
Build Pipeline — What Gets Built When
1
Map Topology Registry (manual + algorithmic)
Create maps/topology.json with structural properties for each existing map. Mode affinity vectors require playtesting annotation for now; algorithmic derivation from map geometry is a Phase 2 task.
Phase 1
2
Bot profile parameter set in compiler output
The compiler selects a bot profile name (one of 6) and passes it to server.js with the session config. server.js uses it to override bot_type and bot_aggression to match the profile. Profiles stored in compiler.js as constants.
Phase 1
3
Map selection added to compiler
Compiler reads topology.json and selects the map with highest mode_affinity[target_mode] subject to recency penalty (don't repeat the last 3 maps). Currently map_idx is passed through unchanged from admin or defaulted.
Phase 1
4
Behavioral signal extraction from session records
Extract archetype_tag and strategy_shift_count from round_snapshots and add to Ledger observation. Requires defining the signal extraction formulas and wiring them into _writeSessionObservations.
Phase 1
5
Strategy pattern library (aggregate from Ledger)
After ≥ 20 sessions per map, aggregate behavioral signals into per-map pattern records. This powers tempo_delta, opening_distribution, and chokepoint behavior comparisons. A nightly or on-demand compute job, not real-time.
Phase 2
6
Per-student map Elo matrix
Extend the compiler's Elo computation to produce a [modes × maps] matrix per student rather than a [modes] vector. Requires enough per-map session count for each student — gated behind Phase 2 data accumulation.
Phase 2
7
THEORETICIAN bot from theoretical optimal
Once theoretical optimal strategies are documented per map per mode, the THEORETICIAN bot executes them. This may require the game's bot AI to accept a move-sequence directive rather than a scalar aggression parameter — a server.js game engine change.
Phase 2
8
Adaptive bot (ADAPTOR profile)
The ADAPTOR bot requires real-time read of the student's current session state and strategy inference mid-game. This is the most technically demanding bot profile — it needs in-game signal processing, not just session-level configuration.
Phase 3
9
Full composition optimization (argmax E[KL] over map × bot)
The compiler optimizes all three dimensions simultaneously — mode, map, bot profile — using fitted parameters from Phase 3. Until then, heuristic rules from the composition table in Section 5 approximate the optimization.
