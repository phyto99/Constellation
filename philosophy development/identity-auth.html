The Four Identity Tiers

Identity tier determines what the student receives from the system — not whether they can play, and not whether the system records the session. The game is fully functional at every tier. The cognitive model activates progressively as identity becomes more certain.

The core rule: Consent affects what the student sees, not what the Ledger records. The Ledger is append-only; it records all outcomes at Layer 0. Attribution and visibility are Layer 1 decisions — derived views, not stored values. A player who never signs in still affects every other player's model through session outcomes.
Tier 0 — Anonymous Guest
No name · No account · Session token only
Zero friction
A player who clicks "play as guest" and gives nothing. They receive a session-scoped token stored in localStorage — a random UUID generated on first visit, never linked to any name or contact. No PII is ever collected. COPPA does not apply. GDPR does not apply. The system records their outcome in the Ledger tagged with that session token, but the record is not attributed to a person — it is attributed to a device session.
What they get: The game works fully. No zone overlay (no compiler history). No personal model in Observatory.
What the system gets: Outcome signal contributing to session calibration (all other players' rank_pct is affected by their score). Aggregate patterns — but not attributed to a student.
Legal status: No consent required. No PII collected. Fully compliant at launch.
Tier 1 — Named Guest
Picks a name · No account · Name stored in localStorage
Current default behavior
The current system. Player enters a name. The server calls resolveStudentId(name) and assigns a stable UUID from the name registry — the same UUID every time they type that name in that browser. Their history accumulates session-to-session as long as they use the same name and the same browser. If they clear localStorage or switch devices, the chain breaks.
What they get: Zone overlay if compiler has run. Personal history accumulates. Shows in Observatory as "unconfirmed" (name-hash icon). Cannot see their own Layer 1 model (not exposed to students without explicit consent).
What the system gets: Confirmed-quality signal because the name→UUID mapping is stable within a browser. student_id_confirmed: true (currently) but without actual identity verification.
Legal status: Gray area. If the name is not real (e.g. "PlayerX"), no PII is collected. If the name is real, it is PII. Best practice: add a brief notice at name entry — "Your name is used to remember your progress. No account required."
COPPA: If name entry is not linked to real identity, no verifiable consent is required. The risk is low but not zero.
Tier 2 — Registered
Email or Google · Age gate · Explicit consent
To build
Player creates an account via Google OAuth or email/password. Age gate applies at registration: if under 13 (US) or under 16 (EU), parental consent flow is triggered. Consent is recorded with policy_version and timestamp. The student's UUID in the registry is linked to their Google ID or verified email, making it cross-device and permanent.
What they get: Full zone overlay. Personal Layer 1 model visible at appropriate Progressive Unlock tier (BASELINE → DEVELOPING → ALPHA). Cross-device persistence. Data export. Deletion rights self-served.
What the system gets: Verified identity, explicit consent on file, cross-device session chain, long-term model with no chain breaks.
Legal status: COPPA compliant if age gate is implemented and parental consent flow works for under-13. GDPR compliant if consent is explicit and granular. Privacy policy must be linked at signup.
Claim path: A Tier 1 "Alex" who registers as "Alex" on the same browser can be offered their historical sessions as a merge (teacher can also merge from Observatory).
Tier 3 — School SSO
Clever · ClassLink · Google Workspace for Education · Canvas
Highest value · Build after Tier 2
Student arrives via their school's SSO provider. The school district has already signed a DPA covering student data. COPPA and GDPR consent are handled by the school as data controller — no student-facing consent flow is required, no age gate, no parental consent. The student just clicks "sign in with school" and is in.
What they get: Everything in Tier 2, plus: grade level, class roster, teacher linkage. The cognitive model is embedded in their school context, not a personal consumer app.
What the system gets: Verified grade level (age-appropriate content guaranteed), stable Clever/ClassLink ID (survives school year changes, name changes, even district data resets), teacher can see the model in the correct class context.
Legal status: Best possible. School DPA is a blanket authorization. No per-student consent required. This is how every serious EdTech operates at scale in the US.
Why Clever first: ~70% of US K-12 districts use Clever. One Clever integration unlocks most of the US school market without any additional per-district work.

Authentication Provider Stack

Ordered by ROI for Constellation specifically. Clever alone unlocks 70% of the US school market. Google alone covers most consumer teens. The combination covers nearly every context.

The fundamental split: school context vs consumer context.
School context (Clever, ClassLink, Google Workspace for Education): DPA covers consent, COPPA is handled, no age gate needed.
Consumer context (Google personal, email/password): age gate required, parental consent flow required for under-13.
These are architecturally different flows. Build them separately.

Tier 3 Providers — School SSO

Clever Build First
~70% of US K-12 districts · 25M+ students · Free for schools
Clever is the dominant school SSO in the United States. Students log in with their school credentials — Google, Microsoft, or Clever password — and get redirected to your app with a Clever token. From that token you get a stable Clever student ID, first name, grade level, and school/district association. The school has already done the DPA work; you get all of this without any student-facing consent flow.

There are two integration modes:
Instant Login — school purchases your app, it appears in every student's Clever dashboard. Student clicks your icon, arrives in Constellation already authenticated. This is the school procurement path.
"Log In with Clever" button — you add a button to your own site. Student clicks it, authenticates with school credentials, arrives in Constellation authenticated. This is the direct-to-student path.

Build both. The button unlocks the consumer path for school students. The Instant Login is what you get after a school buys you.
npm install passport-clever
GET /auth/clever → passport.authenticate('clever', { scope: ['read:student_id', 'read:sis'] })
GET /auth/clever/callback → exchanges code, gets { clever_id, name, grade }
Scope 'read:student_id' gives stable ID. 'read:sis' gives grade/school. No email exposed (COPPA-safe).
ClassLink Second priority
~30% of US K-12 districts · Often used in districts that don't use Clever
ClassLink is Clever's main competitor. Most districts use one or the other, rarely both. The integration is architecturally identical — OAuth2, you get a stable student ID, grade level, school association. Prioritize after Clever because the market share doesn't overlap: ClassLink users cannot use Clever, so this is incremental coverage.
npm install passport-classlink (or implement OAuth2 directly with ClassLink docs)
GET /auth/classlink → OAuth2 authorize endpoint
GET /auth/classlink/callback → exchanges code, gets { classlink_id, name, grade }
Google Workspace for Education
Detected at OAuth2 stage via hd (hosted domain) parameter
When a student signs in with Google and their Google account is a school-managed Workspace for Education account, Google returns an hd (hosted domain) field in the OAuth response — e.g. "hd": "school.edu". If hd is present, the student is in school context: their district's DPA likely covers Constellation (or you request they sign a standard Google for Education DPA). No age gate needed; the school manages age verification.

If hd is absent, the student is in consumer context: age gate is required.

This distinction is handled in the same Google OAuth flow — you just branch on whether hd is present in the token response.
npm install passport-google-oauth20
scope: ['openid', 'profile', 'email']
In callback: if (profile._json.hd) → school context, skip age gate
else → consumer context, trigger age gate
Canvas LTI Lower priority
LMS embedding — teacher adds Constellation as an LTI tool inside Canvas
Canvas LTI is not an SSO provider — it is a Learning Management System integration standard. When a teacher adds Constellation as an LTI 1.3 tool in Canvas, students click a link inside Canvas and arrive in Constellation pre-authenticated via a signed LTI launch. The LMS passes student ID, name, and course context. Useful for deep classroom integration but significantly more complex to implement than OAuth2. Build after Clever and ClassLink are live and you have school demand.

Tier 2 Providers — Consumer Registration

Google OAuth2 (consumer) Core consumer auth
Universal · Any Google account · Most teens have one
The highest-friction-to-value ratio for consumer signups. Most teens have a Google account. Sign-in-with-Google requires no password creation, no email verification. After OAuth callback: check hd to determine context. If consumer context: run age gate (birth year selector). If under 13: trigger parental consent flow before account activation.
Same passport-google-oauth20 strategy as above.
If !hd and !age_verified → show age gate before completing registration.
If under 13 → flag account as pending_parental_consent, redirect to parent flow.
Microsoft / Azure AD Optional
Dominant in enterprise school districts; less common in K-12 than Clever
Many districts use Microsoft 365 for Education. Students have school Microsoft accounts. Similar school-context detection: if the tenant is a school tenant, DPA covers consent. Implement after Clever if you encounter Microsoft-heavy districts. The passport-azure-ad strategy handles this.
Email / Password Fallback
Universal fallback · Higher friction · Required for Tier 2 completeness
Some parents and students won't use Google. Email/password with bcrypt is the fallback. Email verification required before account activation. Age gate at registration. Under-13: parental email + consent token (parent receives email, clicks link, activates account). This is the most complex COPPA-compliant path — email-based verifiable parental consent is the only method explicitly approved by the FTC.
npm install bcryptjs nodemailer (or use Mailgun/SendGrid for email)
POST /auth/register → hash password, send verification email, set pending_verification: true
GET /auth/verify/:token → activate account, trigger age gate if under 13
For under-13: POST /auth/parent-consent/:childId → send consent email to parent address

The Simplest Possible Starting Stack

Phase 1 (now): Google OAuth2 only. Consumer + Workspace for Education detection. Age gate for non-school Google accounts. This covers most teens immediately, requires one OAuth integration, and gets you COPPA-compliant for Tier 2 users.

Phase 2 (month 3): Add Clever. This unlocks school procurement. You can now sign a school DPA and tell districts "students can log in with their Clever account."

Phase 3 (school demand): ClassLink, Microsoft, Canvas LTI, email/password as needed.

The Upgrade Path — Tier 1 → Tier 2

A Named Guest who later registers is offered their session history. This works because the name-based UUID is deterministic — if they registered with the same name from the same browser, the system can propose a merge.

The merge offer: After Google login, the server checks if localStorage has a playerName value. If it does, it calls resolveStudentId(name) to get the name-hash UUID, then checks if that UUID has any ledger records. If yes: "We found 7 sessions recorded under the name 'Alex' in this browser. Would you like to link them to your account?" One button press triggers a teacher-style merge: name-hash UUID → google account UUID. Append-only: the merge event is recorded in the ledger.

Friend Invite Flow

Player A is registered (Tier 2). They create a game room. They share the room link with friends. Friends arrive at the room URL. What happens?

Option 1 (current behavior): Friends land on the game page, see the identity screen, choose their tier (anonymous, named, or sign in). Each friend's data is attributed independently. The game works immediately. Player A's model is updated based on the full session outcome. Friends who chose anonymously contributed to the session but don't accumulate their own model.

Option 2 (future): A friend invitation link carries a ?ref=playerA_id parameter. The system pre-fills a "join as guest, your friend A invited you" screen. Their identity is still their own choice — but the social graph is recorded in the session for future social dimension analysis (Q5).

Mixed-Consent Sessions

A single game session will routinely have players at different identity tiers. This is normal and expected. The system handles it correctly at Layer 0 — each player's record is tagged with their own identity tier and consent status. No one player's choice blocks anyone else from playing.

What Anonymous Players Contribute

An anonymous player in a 4-person game reduces the noise in everyone else's rank_pct signal. Without them, a 3-player game has a coarser ranking (1/2/3). With them, the ranking is more informative. Their presence is signal even if their identity is unknown. The system treats them as real competitors for rank purposes — which is what they are.

They get
  • Full game experience
  • All game features
  • Zone overlay — only if a prior session was recorded for their anon token AND the teacher ran the compiler for that token (rare)
The system gets from them
  • Session outcome (rank, score)
  • Signal that improves other players' rank_pct precision
  • Behavioral signals (archetype_tag, strategy_shift_count) — recorded but not attributed
  • Nothing linkable to a real person

The Rule: One Student's Decision Never Blocks Another's Data

Player A's full model does not depend on Player B's consent status. Player B's anonymity does not corrupt Player A's Elo. The session is independently attributed — each player's record is their own row in the Ledger, their own Elo update, their own model. The only thing shared is the rank_pct calculation, which is computed from the actual game outcome regardless of who is consented. This is the correct architecture.

The JWT Payload (What Gets Sent to the Game Client)

When a player is authenticated, the server issues a JWT stored in localStorage or a cookie. The game client includes it in the joinById options so the server can verify identity without a round-trip.

JWT payload — passed as joinById options.token
{
"sub": "uuid", // student UUID from registry
"name": "Alex",
"tier": "clever",
"consent_source": "school_dpa",
"grade": 9,
"iat": 1718000000,
"exp": 1718086400 // 24 hours
}

Server onJoin Change

Currently: onJoin resolves identity from options.name. New: if options.token is present, verify it and extract the student ID and tier directly — no registry lookup needed.

server.js — ConstellationRoom.onJoin (diff)
onJoin(client, options) {
const player = new Player();
if (options.token) {
const jwt = verifyJWT(options.token); // throws if invalid/expired
player.studentId = jwt.sub;
player._studentIdConfirmed = true;
player._identityTier = jwt.tier;
player._consentSource = jwt.consent_source;
player.name = jwt.name || options.name || 'Player';
} else if (options.name) {
const resolved = ledger.resolveStudentId(options.name);
player.studentId = resolved.id;
player._studentIdConfirmed = resolved.confirmed;
player._identityTier = 'named_guest';
} else {
// Anonymous
player.studentId = options.anonToken || ledger.nameToId('');
player._studentIdConfirmed = false;
player._identityTier = 'anonymous';
}
...
}

Layer 1 Change: Filter by Consent Before Surfacing

The compiler already runs for all confirmed students. The change: before the compiler output is surfaced to a student's own view (their personal model page), check consent_source. Named guests see nothing personal — only teacher sees their Observatory entry. Registered and SSO students see their model at the appropriate Progressive Unlock tier.

Named guests in the Observatory: Teacher sees them with a ⚠ unconfirmed badge. Clicking their row shows: "This player is a named guest. Their history is recorded and their model is computed. To give them access to their own model, ask them to register and link this name." Teacher can trigger a merge from the Observatory once the student registers.
