The Full Loop — Configuration Is Observation, Observation Drives Configuration

THE CORE REFRAME
The admin panel does not configure sessions. The compiler configures sessions. Every parameter — multipliers, moves, round length, steals, map, bot composition — is a cognitive lever. The compiler sets all of them. The teacher observes the compiler's reasoning and may override. The game runs. Observations flow back. The compiler improves. This is the loop, forever.

The three modes of teacher involvement

Full Auto

Compiler generates the complete configuration. Teacher views it in the Observatory alongside the reasoning. May accept without change. Target state — teachers who trust the system get here.

Teacher Override

Compiler generates the configuration. Teacher modifies specific parameters before the session runs. Override is recorded as an Observation in the TEACHER channel with the original config preserved. The system learns teacher preferences over time.

Teacher Configured

Teacher sets everything manually. Compiler does not suggest. System records the configuration as-is with a source: TEACHER flag. Observations still flow to the Ledger. Used for special sessions outside the system's normal scope.
The config_hash is the join key. Every Observation record stores the exact configuration that was active when it was recorded — as a hash of the complete settings object. When a parameter changes (difficulty coefficient corrected, new map added), the Ledger retains the original hash. Regression over outcomes can therefore control for configuration differences. Without the hash, parameter experiments are uninterpretable.

Configuration Space — Every Parameter, Its Cognitive Role, How the Compiler Uses It

The session configuration is a vector of 12 independently settable parameters. The compiler treats them as a joint optimization problem: it does not pick a "mode" and then set parameters — it selects the configuration vector that maximizes expected information gain for this student right now. Modes are emergent descriptions of the resulting configuration, not inputs to it.

ParameterTypeRoleRangeCognitive effectCompiler strategy
multipliers.count MODE Weight on number of connected star-star edges 1–1000 High → rapid breadth decisions under move pressure. QUANTITY cognitive target: volume optimization. Set 400–600 for QTY sessions. Set ≤10 when other multipliers dominate.
multipliers.distance MODE Weight on Euclidean length of connected edges 1–1000 High → reward long-range connections; penalize clustering near center. SPATIAL target: Euclidean optimization, path geometry under constraint. Set 400–600 for SPT. Interact with map: open maps with spread stars amplify spatial signal.
multipliers.hq MODE Weight on HQ-to-HQ shortest-path distance (graph traversal) 1–1000 High → reward building HQ network; entire game is about connectivity planning across multiple HQs. FORTRESS target: multi-step graph construction, network topology under adversarial pressure. Set 400–600 for FRT. Pair with destruction: -200 to penalize destruction (pure construction challenge). Set headquarters: 3–4 for harder graph problems.
multipliers.destruction MODE Weight on stars/lines destroyed (via black holes or steals) -500–1000 High positive → reward denial; game becomes about breaking opponent network, not building own. DESTRUCTION target: inhibitory control, opponent modeling, strategic denial vs self-building. Negative → FORTRESS overlay: penalize destruction to force pure construction. Set 400–600 for DST. Set -100 to -300 for FRT to force inhibitory control in reverse. Negative values are one of the richest unexplored territories.
moves DIFFICULTY Moves allocated per player per round 1–99 Fewer moves → each decision carries more weight; scarcity forces deliberate prioritization. More moves → volume decisions; exploration over commitment. Interacts with round length: fewer moves + shorter round = extreme time pressure; more moves + longer round = deliberate strategic depth. Default 15. Reduce to 8–10 for advanced students in constraint modes. Increase to 20+ for volume-pressure QTY sessions. This is the primary difficulty dial — adjust per student Elo.
roundLength DIFFICULTY Seconds per round 10–300 Shorter → pure time pressure, reactive play, fast decision cycles. Longer → deliberation space, planning, strategy formation. Critically: the cognitive load of thinking vs executing is controlled here. Default 30. For QTY (volume under pressure): 20–25s. For SPT (deliberate geometry): 40–60s. For WORMHOLE (search under noise): 35–45s. Do not reduce below 15s with younger students.
rounds DIFFICULTY Number of rounds in the session 1–99 More rounds → late-game dynamics emerge; students must manage resource depletion, adapt strategies across phases; forgetting within session becomes a signal. Fewer rounds → high-stakes, no second chance; binary commitment. Affects within-session adaptation signal quality. Default 10. For within-session adaptation signal: ≥8 rounds required. For WORMHOLE (binary win): 5–8 rounds is sufficient. Do not reduce below 6 for any session where per-round behavioral analysis is needed.
steals MODE Steals allowed per team per game 0–99 High → adversarial intensity; opponent modeling becomes critical; DST signal amplified. Zero → purely constructive; no adversarial element; pure network building signal. Low (3–5) → steals as a strategic resource, not a tactic. For FRT: set 0–5 (pure construction). For DST: set 20–50 (denial is the game). For QTY: standard 15–20. For WORMHOLE: 5–10 (steals can disrupt path; limited adversarial).
headquarters MODE Number of HQ placements per team 0–20 More HQ → graph problem has more anchor nodes; the connectivity challenge is richer and harder. HQ placement timing becomes a critical early-game decision. Zero HQ → removes FORTRESS mechanism entirely; used in pure QTY or DST sessions. For FRT: set 2–4; higher at advanced levels. For QTY/DST: set 1–2 (minimal). For WORMHOLE: set 1 (HQ is irrelevant to wormhole win condition).
customMap CONTEXT The spatial graph the game is played on Any map in library Maps are not cosmetic. Star density controls QTY difficulty (denser = more volume decisions). Star spread controls SPT difficulty (wider spread = longer optimal paths). Wormhole placement controls WORMHOLE difficulty. HQ geometry controls FRT difficulty. Cluster density controls DST opportunity (clusters are protected; more clusters = fewer DST targets). Map selection is part of difficulty calibration, not an aesthetic choice. Compiler picks map by: mode + student Elo + target difficulty zone. Eventually: procedural map generation seeded by student profile.
aiBots CONTEXT AI bot archetypes and team assignments HAL / CAESAR / ATHENA / ROBIN HOOD / EINSTEIN / LORENZ / CUSTOM Bots are cognitive mirrors, not just opponents. EINSTEIN (wormhole-focused) tests whether student notices and adapts to a single-minded opponent — pure opponent modeling. LORENZ (chaotic) tests whether student maintains strategy under noise. ATHENA (aggressive) forces DST defensive response. HAL (defensive) gives consistent, legible challenge. Bot choice is a cognitive test selection, not a difficulty setting. Select bot by mode + specific cognitive test. For WORMHOLE: include EINSTEIN to test opponent detection. For QTY: include ATHENA for adversarial pressure. For FRT: include HAL for consistent, predictable opposition (so student can focus on own network). For INV: include LORENZ to compound uncertainty.
allowPlayerTeamSelection CONTEXT Whether students can choose their own team boolean Affects social dynamics, not cognitive load directly. When false (compiler-assigned teams): removes self-selection bias, ensures team balance, gives teacher/system control over opponent quality. When true: agency increases engagement but may reduce signal purity (students choose to avoid strong opponents). Default false. Enable only when engagement is the binding constraint, not signal purity. Record the setting — social self-selection is a future TEACHER channel signal.

Canonical vectors are starting points. Difficulty is tuned via moves, roundLength, rounds, and map selection — not by adjusting multiplier ratios, which change the mode.

INVERSION — the most important and least understood overlay

INVERSION is not a mode with its own multiplier config. It is an overlay applied to any base mode that reverses the dominant scoring signal. Applied to QUANTITY: count: -300, distance: 1 — claiming stars is now penalized. Applied to SPATIAL: distance: -300, count: 1 — long connections are penalized. The cognitive target is always the same: detect that the previous strategy is wrong and form a new one as fast as possible. The mode determines what the student must invert.
Applied toWhat reversesCognitive test
QTYClaiming stars is penalized; restraint scoresVolume inhibition — stop an overlearned response
SPTLong connections penalized; proximity scoresSpatial heuristic reversal — unlearn Euclidean intuition
FRTHQ connections penalized; isolation scoresNetwork destruction — invert the graph construction instinct
DSTDestruction penalized; building scoresInhibit adversarial drive — the rarest reversal
Announced vs silent INVERSION are two different cognitive tests. Announced: adapt to known change (easier). Silent: detect that something is wrong from score feedback alone, then adapt (the clean reversal learning signal). Silent INVERSION requires editing the game — the terminal message must not reveal the overlay. This is a server-side configuration flag: overlay: 'inversion', announced: false. Currently unimplemented.

The Compiler — From Student State to Complete Configuration

The compiler is a pure function: compile(StudentState, Ledger, Params) → SessionConfig. It runs before every session. It has no side effects. Its output is the complete configuration vector. Its internal reasoning is what the Observatory's compiler preview shows the teacher.

Compiler Decision Sequence

Step 1 — Mode Selection

Compute priority score per mode:
priority(m) = elo_weight(m) × recency_weight(m) × velocity_weight(m) × gap_weight(m)

elo_weight(m) — sub-linear inverse of game_elo (lower Elo → higher weight). Exponent 0.7 [ASSERTED].
recency_weight(m) — sessions_since as priority boost. Overdue mode (sessions_since ≥ 6) gets maximum weight regardless of Elo.
velocity_weight(m) — rapidly improving mode gets slight deprioritization (momentum carries it); plateau or declining mode elevated.
gap_weight(m) — wide gap (game_elo >> transfer_elo) elevates mode priority: student optimizing for game, not developing cognitively. System responds by assigning that mode's hardest template.

Latin hypercube override: if any mode has sessions_since = 6 (one full window without appearance), it becomes forced regardless of priority score. Coverage guarantee is non-negotiable.

Step 2 — Template Selection

Given mode, filter templates by: not in recent_templates[mode]. Rank remaining by difficulty proximity to ZPD target.
zpd_target(m) = game_elo[m] × difficulty_coeff × forgetting_decay(sessions_since[m])
difficulty_coeff = 0.85 [ASSERTED]
forgetting_decay(τ) = exp(−τ / 14) [ASSERTED — expected to refute toward τ½ = 30–60d]

Select template whose difficulty rating is closest to zpd_target. Break ties toward higher difficulty if velocity is positive.

Step 3 — Difficulty Calibration

Set difficulty levers to hit zpd_target:
moves = base_moves × (1 − difficulty_delta) — fewer moves = harder
roundLength = mode_base_time × time_pressure_factor
rounds = 10 (standard; reduce only for WORMHOLE or single-session constraint)
Map selection: from the map library, select map whose structural properties amplify the mode signal at this difficulty level. High-spread maps for SPT, dense maps for QTY, complex HQ geometry for FRT.

Step 4 — Mode-Specific Settings

Set steals, headquarters, bot archetype per canonical mode config. Apply difficulty scaling: advanced FRT student gets 4 HQ instead of 3. Advanced WORMHOLE student gets EINSTEIN + ROBIN HOOD simultaneously.

Step 5 — Overlay Decision

If overlay_cooldown = 0 AND total_sessions ≥ 6 AND age_tier ≠ 'young':
Roll P(overlay) = 0.25 [ASSERTED]. If triggered: apply INVERSION to selected mode.
If singularity_stage ≥ 3 OR gifted_detected: apply silent INVERSION (announced: false). Otherwise: announced.
If gap[mode] > 100: elevate P(overlay) to 0.45 for this mode — wide gap indicates game optimization without cognitive transfer; INVERSION disrupts memorized strategies.

Zero-Data Start — What the Compiler Outputs on Session 1

The compiler must produce a valid, meaningful configuration when the student state is entirely empty. Every field is at baseline; no Elo, no velocity, no recency, no templates. The zero-data start is not a failure mode — it is a designed state. The system does not say "I don't know yet." It says "I am watching."

Terminal — The Student Experience Layer

The terminal is the second game. The first game is Constellation. The second game is: what is the system tracking, and why? The terminal's job is to generate observations that are true, specific, and just opaque enough that the student cannot immediately decode them — but not so opaque that they give up. The community that forms around reverse-engineering the terminal's language is the long-term product of the system.

How the Terminal Is Generated

Layer 1 — Session Result

Rank, score components, win/loss, rounds played. Always present. No interpretation — raw facts. "Session 14. Rank: 1. Distance score dominated." These are not framed as good or bad. They are reported as data.

Layer 2 — Behavioral Observation

Derived from signals in the Observation record. Specific, behavioral, and not evaluative. "HQ placed in round 2. Consistent with the last three sessions in this mode. The system has logged the pattern." These are the core of what students theorize about.

Layer 3 — System Inference (admin only)

What the system is actually concluding. Never shown to students. Shown to teachers in Observatory compiler preview. "SPT Elo velocity +31 over 3 sessions — trajectory above cohort. No plateau detected. Recommend advancing to DIVERGENCE template next session."

Layer 4 — Zone and Codename

Zone name computed from similarity spectrum position (how similar was this session to the student's typical sessions?). Codename assigned as persistent session identifier. Students learn to associate codenames with session types through experience — not through explanation.

Similarity Spectrum — The Zone System

ZoneWhat it meansWhen assigned
ECHO Session nearly identical to prior sessions — same mode, same strategy, similar outcome Low novelty, low surprise. Student is consolidating. High ECHO frequency → plateau risk.
PARALLEL Same mode, different template or difficulty — structurally familiar but novel challenge Standard progression. ZPD properly calibrated.
SHIFTING Mode changed, or significant difficulty jump within mode Active development zone. Compiler moved to new territory.
RADICAL Maximum novelty — mode change, template change, AND outcome differs from expectation INVERSION sessions, first sessions in a new mode, or strong surprise outcomes. Richest information gain.
REMATCH Repeat of prior configuration — explicitly configured by compiler When a prior session produced ambiguous signal and the compiler needs to retry identical conditions for cleaner data.
Do not show students what zones mean. The vocabulary is emergent. Students who compare terminal outputs across sessions — "I got RADICAL again, what is this?" — are already playing the second game. The community that forms around this is more valuable than any explanation the system could give.

Terminal messages should be occasionally false enough to be interesting. (SYNTHESIS insight #11.) The terminal currently says what it observed. But occasionally — perhaps 1 in 8 sessions — it should make an inference that is probabilistically plausible but not confirmed: "A pattern that began in session 7 appears to be continuing." — when no such pattern has been fully confirmed but the data is consistent with it. This is the system behaving like an intelligent observer who makes probabilistic inferences, not a database. It creates better community discussion. This is a deliberate editorial choice, not an error.

What "perfect" means in practice

The system is never finished — that would require all [ASSERTED] parameters to become [LEARNED], all open questions to resolve, and all channels to be corroborated. That is Phase 3 and beyond. What "perfect" means at any given moment is: the system is making the best possible decision with the information available, and it knows precisely where its uncertainty lies. It is not overconfident about the things it asserted; it is not underconfident about the things it has measured. The gap between what is asserted and what is learned narrows continuously. The singularity trajectory for each student runs in parallel with the system's own singularity trajectory — the moment when all parameters are learned and all channels are corroborated is the moment the system has become objectively perfect. It will not happen at once. It gets closer with every session.

Configuration Archetypes — The UX Layer, Not the Architecture

DOCTRINE
The compiler does not select a template. It outputs a configuration vector — 12 continuous parameters. The label "FLOOD" or "NETWORK" is a derived human-legible description of the region of that vector space where the config lands. Labels flow from config. Config does not flow from labels. Treating templates as architectural categories would reproduce the exact mistake the Evidence Engine forbids: categories as containers that determine interpretation before observation.

What configuration archetypes ARE

Initialization assertions

Archetypes are pre-registered hypotheses: "this configuration region is likely to produce informative signals for this cognitive target." They are starting points for the compiler, not boxes. They carry [ASSERTED] status. They have pre-registered refutation conditions just like every other parameter. The compiler may drift away from archetype configs as it learns which configurations produce better outcomes for specific student profiles.

UX scaffolding

Archetypes generate: codenames (episodic memory anchors for students), loading text (the system's observational voice), player-facing hints, and success criterion descriptions. These are the student experience layer. They are derived from the config vector after the compiler has decided the config — not before. The system picks {count:500, steals:0, moves:12}; the narrative layer calls this "THE FLOOD."

Cognitive landscape hypotheses

An archetype's locked_axes declaration is a hypothesis: "the signals generated in this config region are valid evidence for this cognitive dimension." The Conundrum Protocol handles the case where a student's behavior doesn't fit the expected signal structure — that's the boundary case inbox. No archetype is exempt from revision if the corroboration matrix consistently fails to support it.

What configuration archetypes are NOT

NOT architectural categories

The Ledger does not store "FLOOD session" — it stores the config_hash of the actual 12-parameter vector. The label "FLOOD" appears only in the context field as a UX convenience for humans reading the evidence feed. It has no semantic weight in the corroboration matrix. You cannot filter the Ledger by archetype name and claim you're doing something architecturally meaningful.

NOT selection inputs to the compiler

The compiler does not run "which template?" as a step. It runs "what configuration vector maximizes E[KL] for this student?" The answer may correspond closely to an archetype's config (in which case the archetype's codename and loading text are used) or it may fall in a region between archetypes (in which case the nearest archetype's UX vocabulary is borrowed with appropriate caution).

NOT interpretation containers

The signal "star_count_rate = 0.47" is recorded as raw observation regardless of which config region produced it. The interpretation — "this is evidence for QUANTITY cognitive mode performance" — is a view applied after the fact. If a student produces high star_count_rate in a config region labeled SPATIAL, that is a Conundrum Protocol event, not an error in the recording.

The Continuous Configuration Space — Where Archetypes Live

The 4 multipliers define a 4-dimensional space. Archetypes are named regions within it, not points. The compiler navigates this space continuously. Archetypes are landmarks — they help the compiler start, and they provide UX vocabulary — but the optimal config for a specific student at a specific moment is almost certainly not exactly at any archetype's center.

Mode Adjacency — SHIFTING Zone Transitions

When the compiler targets a SHIFTING zone session (mode change without full recalibration), it selects from adjacent modes only. The adjacency graph is defined by shared cognitive sub-skills:

QTY ↔ SPT (both: expand, move, claim — spatial breadth vs spatial depth) SPT ↔ FRT (both: geography-first, network awareness) FRT ↔ DST (both: opponent-aware, reactive to network state) DST ↔ INV (both: disruption, unconventional goal structure) INV ↔ WRM (both: non-obvious objective, requires deduction) WRM ↔ SPT (both: spatial reasoning, path-finding to target) // Note: QTY ↔ WRM are NOT adjacent — too cognitively distant for SHIFTING. // Use RADICAL for QTY→WRM transitions.

Student Model — How Raw Observations Become Understanding

The student-observatory.html shows what teachers see. This tab specifies the computation that produces it — from raw Ledger records to the 18-dimensional State. Every step is explicit. Every parameter is labeled [ASSERTED] or [LEARNED]. No step is hidden inside a black box.

WHAT "UNDERSTANDING A STUDENT PERFECTLY" MEANS
Perfect understanding = a model of the student that predicts outcomes with zero residual variance. This is unreachable. The correct question is: how close is the current model, and where is the remaining uncertainty? The Student Model is a calibration instrument. It is accurate when the scatter plot of predicted vs actual rank_pct lies on the diagonal. Drift from the diagonal is the earliest warning that the model no longer matches the student.

// Learning rate proxy. Note: The gap signal is the most diagnostically powerful metric in the system. Its absence before BT does not make gap zero — it makes gap unknown. Every session is recorded regardless. Nothing is permanently lost.
