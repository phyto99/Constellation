Part I · Section 1
The Map as a Structured Variable

Currently, map_idx is a single integer in the config vector — treated identically to round_length_s or steals. The system knows it used map 3, but knows nothing about map 3. This is the same as a chess engine that records which board was used but doesn't know the rules vary by board.

A map is a structured environment with topological properties that determine which cognitive modes are favored, which human strategies emerge, and which bot behaviors produce the most informative sessions. The compiler must understand this to select the right map for a given student's development target.

The current blind spot: a student with high QTY Elo placed on a map where quantity play is impossible gets a contaminated signal — the outcome reflects map topology, not cognitive skill. The system currently cannot distinguish these.

The resolution requires three layers: a topology registry (what is each map), a strategy pattern library (what humans do on each map), and a bot calibration system (how to create the maximally informative opponent for each student-map combination).

Part I · Section 2
Map Topology Registry — What the System Needs to Know

Every map needs a topology record. This is not derived from play data — it is structural, derivable from the map definition itself. Some properties can be computed algorithmically; others require manual annotation.

Symmetry Class
Rotationally symmetric, bilaterally symmetric, or asymmetric. Symmetric maps make QTY/SPT strategies predictable across player positions. Asymmetric maps favor positional reasoning and force role differentiation.
HQ Geometry
How far are HQs from each other, from the map center, and from neutral resource clusters? Short HQ distance favors FORTRESS play. Long HQ distance favors SPT/distance-seeking strategies.
Resource Density
How many capturable positions exist, and how clustered or dispersed are they? High-density maps favor QTY (capture everything). Sparse maps force selective sequencing and spatial planning.
Chokepoint Count
How many bottleneck positions exist where territory control is decisive? High chokepoint maps reward spatial occupation and position holding. Low chokepoint maps reward open maneuvering.
Mode Affinity Vector
A [6]-dim vector over [QTY, SPT, FRT, DST, WRM, INV] rating how much each mode's scoring strategy is viable on this map. Example: a tight, HQ-centric map: [0.4, 0.6, 0.9, 0.3, 0.5, 0.7]. Used by compiler to select maps that match the target mode.
Opening Divergence
Do most players open similarly, or do opening moves diverge widely? Low-divergence maps have a dominant first move. High-divergence maps produce more varied data per session.
Theoretical Optimal
The provably or empirically best strategy for each mode on this map. Derived from top-percentile sessions or simulation. Used as the THEORETICIAN bot's playbook and as the baseline for measuring student gap.
Difficulty Rating per Mode
How much does this map add to cognitive load for each mode? A map where QTY is easy (many close clusters) vs where QTY is hard (resources dispersed). NOT YET ASSERTED — needs empirical data from Phase 1.

The topology record is stored as a static JSON file (maps/topology.json), updated when new maps are added, and loaded by the compiler at session generation time. It does not go in the Ledger — it is environmental metadata, not an observation.

// maps/topology.json — structure { "0": { "name": "Map Alpha", "symmetry": "bilateral", "hq_distance_norm": 0.72, // 0=adjacent 1=opposite corners "resource_density": 0.61, // 0=sparse 1=saturated "chokepoints": 3, "mode_affinity": [0.7, 0.5, 0.8, 0.4, 0.5, 0.6], // [qty,spt,frt,dst,wrm,inv] "opening_divergence": 0.4, // 0=everyone plays the same, 1=fully random "theoretical_optimal": { "qty": [...], "spt": [...] }, "difficulty": { "qty": 0.45, "spt": 0.65, "frt": 0.30 } } }
Part I · Section 3
Strategy Pattern Library — What Humans Actually Do

Beyond the topology, the system needs to know what human players actually do when placed on each map. This is empirical knowledge accumulated from the Ledger — not derivable from the map structure alone.

The pattern library serves two purposes: it tells the compiler what this student's behavior on this map looks like vs. what most students do, and it gives the bot calibration system enough context to create a bot that plays against the student's specific tendencies — not just against generic play.

Pattern DimensionWhat it measuresHow it's capturedHow it's used
First-move distribution Where do most players send their first piece on this map? What % claim the central resource vs. the HQ-adjacent resource vs. the far edge? Round 1, move 1 position from Ledger records. Aggregated across all sessions on map_idx=X. Bot can be configured to either play the statistically dominant first move (THEORETICIAN) or to counter the student's documented first move (CONTESTER).
Phase distribution How does the average player's board position evolve round-by-round? Do most players expand in early rounds and consolidate later, or hold and then push? round_snapshots from Ledger → per-round rank_pct curves, averaged across all students on this map. Identifies the typical tempo of the map. A student who is significantly ahead or behind the average tempo curve at round 3 is showing map-specific tempo skill or deficit.
Common archetypes On this map, what strategic archetypes emerge? e.g. "Rusher" (early all-in expansion), "Turtler" (consolidate own territory), "HQ Sniper" (ignore resources, target opponent HQ), "Opportunist" (react to opponent moves). Session-level behavioral signals: early_expansion_rate, hq_attack_frequency, contested_zone_entry, reactive_vs_proactive_ratio. Student gets tagged with their dominant archetype on each map. The bot is selected to counter or mirror that archetype depending on the development target.
Student map fingerprint For a specific student: how does their play on map X differ from their play overall? Do they default to the same strategy regardless of map, or do they adapt? Compare per-map behavioral signals to student's overall mean. High deviation = map-aware player. Low deviation = map-blind player (applies same strategy everywhere). Map-blind players need maps that punish their default strategy. Map-aware players need more complex maps that force higher-order adaptation.
Chokepoint behavior When a chokepoint is available, what % of players take it vs. bypass it? How long do players who take chokepoints hold them? Requires positional data in Ledger (currently not stored). FUTURE Identifies whether students understand positional leverage. A student who consistently bypasses high-value chokepoints is showing SPT deficit on positional maps.

Privacy note: Pattern data is aggregated at the cohort level before being used in compiler decisions. The system does not expose "what most students do" to students — only to the admin panel and to bot calibration. The pattern library is a system resource, not a student-facing feature.

Part I · Section 4
Bot Strategy Profiles — Six Personalities for Maximum Development

The current system treats bot configuration as a single parameter: bot_aggression (0–10). This is a scalar on a behavior that needs to be a vector. Aggression is one dimension of bot strategy. The others are: target selection logic, tempo, and adaptive vs. fixed behavior.

The following six profiles cover the full space of what a bot can do to develop a specific student. Each is defined by its development target — the cognitive dimension in the student it is designed to stress-test.

MIRROR
Target: self-model accuracy
The bot replicates the student's dominant strategy from their Ledger history. If the student always starts with a northern expansion, the bot opens with a northern expansion. The student is playing against a projection of themselves.
Deploy when: student has a strong, consistent strategy and the question is whether that strategy is fundamentally sound or exploitable.
Signal: rank_pct vs. own historical baseline. If the MIRROR bot beats the student more often than vice versa, the strategy has an exploitable weakness.
CONTESTER
Target: adaptability under pressure
The bot specifically targets and contests the zones the student is developing — not the strategically optimal zones. If the student typically develops the right side, the bot occupies and defends the right side, forcing development somewhere unfamiliar.
Deploy when: student is map-blind (plays the same opening regardless of map) or shows low variance in strategy.
Signal: strategy_shift_speed, alternative_axis_discovery. Students who find new approaches quickly show genuine adaptability.
ACCELERANT
Target: tempo and decision speed
The bot plays at maximum aggression in early rounds — claiming as many positions as possible as fast as possible. By round 3, the board state is already contested. The student must respond at a tempo faster than they are comfortable with.
Deploy when: student shows slow early development (round 1–2 rank_pct below average) or high unused move_pool_rate.
Signal: early_response_latency, round_1_rank_pct. Adapting to the accelerant's pace shows temporal flexibility.
TURTLER
Target: initiative and aggression
The bot plays defensively — consolidating a small territory and holding it, rather than expanding. The student must be the aggressor. There is no external pressure forcing action; the student must generate their own momentum.
Deploy when: student is reactive (low proactive_vs_reactive ratio) or when prior sessions show high variance that might mask underlying skill.
Signal: proactive_expansion_rate, initiative_score. Effective expansion against a turtler shows self-generated strategic momentum.
THEORETICIAN
Target: skill ceiling measurement
The bot plays the theoretical optimal strategy for this map and mode, derived from the strategy pattern library. It is not adaptive — it executes the best known fixed strategy. The gap between the student's performance and the theoretician's IS the map-specific skill gap.
Deploy when: student has high session count on this map (≥ 6 sessions) and the compiler needs a clean skill ceiling measurement.
Signal: rank_pct vs. theoretician is the map-mode skill gap. Used in Phase 2 BT transfer calculations.
ADAPTOR
Target: meta-cognitive flexibility
The bot changes strategy mid-session based on what the student is doing. If the student is expanding north, the bot shifts to contest north. The student is not playing against a fixed strategy — they are playing against an opponent who is reading them in real time.
Deploy when: student has high experience on this map and simple strategies no longer produce information.
Signal: counter_detection_speed, strategy_oscillation. A student who deploys deception in response is showing meta-game reasoning.
Part I · Section 5
The Perfect Session — Composing Student × Map × Bot

The compiler's current job is: select mode → build config vector. The future compiler's job is: select mode → select map that best exposes that mode → select bot strategy that maximally develops the student on that map in that mode. Three decisions, not one.

The composition principle: the best session is the one that maximizes expected KL divergence between the student's prior model and their posterior model after the session.

RADICAL zone student Deficit mode Map with HIGH affinity for the deficit mode MIRROR (their dominant mode strategy, now wrong context) Student enters their strongest strategy into a mode that doesn't reward it, AND plays against a bot that does exactly what they do. Double displacement.

PART II — AI MAPMAKER: SPECIFICATION & PHILOSOPHY

A complete specification for an AI system that creates Constellation maps from images, spatial formulas, strategic intent, and mechanical constraints — with full understanding of how the game works and what cognitive experiences each map should create.

Part II · Section 1 — Full mechanical model
What the AI Must Understand — Complete Game Mechanics

The mapmaker AI cannot produce strategically meaningful maps without a complete understanding of how the game works at the mechanical level. Every design decision — star placement, connection topology, HQ position — cascades into strategic affordances.

Stars (nodes)
Stars are capturable positions. A team claims a star by moving a piece onto it. Stars have a type: type 1 (capturable, no special function) and type 2 (HQ — headquarters, high strategic value). Stars do not move.
Map design lever: star density, cluster shape, spatial distribution
Lines (edges)
Lines define which stars are adjacent — i.e., which moves are legal. A piece can move from star A to star B only if there is a line between them. The edge structure determines pathways, chokepoints, and the reachability of each star. Degree = number of edges at a node.
Map design lever: connectivity, degree distribution, bridge structures
Scoring multipliers
count_mult: points per captured star. dist_mult: points per unit of total distance between your stars. hq_mult: points for capturing or proximity to HQ stars. dest_mult: points for destroying opponent's stars. The config vector sets these — the map determines which multipliers are naturally rewarding.
Map design lever: HQ placement determines hq_mult viability; spread determines dist_mult viability
Moves & steals
Each team gets a fixed move pool per round (config: moves). A steal recaptures a star held by the opponent (costs extra from move pool, limited by steals). High steal limits favor contested maps; low steal limits favor spreading and holding.
Map design lever: chokepoint density affects how often steals are contested
Rounds & round length
Sessions have a fixed number of rounds (rounds, default 10). Each round has a time limit (round_length_s). Longer rounds favor deliberate planning; shorter rounds favor fast heuristics. Maps with complex topology penalize short-round play more.
Map design lever: high avg_degree maps are harder to read under time pressure
HQ placement
HQ stars (type 2) can be fixed (embedded in map JSON) or dynamic (teams place their own HQ at the start). Maps with 0 type-2 stars use dynamic HQ placement. Fixed HQ maps create deterministic fortress dynamics.
Map design lever: fixed HQs favor FRT mode; dynamic HQs add positional decision layer
Bot AI (current)
Bot AI is client-side, driven by aggression (0–10). High aggression = expand fast, contest early. Low aggression = consolidate. The bot has no deep strategy awareness — it responds to local state, not global map topology. Phase 1 reality; Phase 2 bot AI is strategy-profile-driven.
Map design implication: maps where early expansion dominates reward high-aggression bots more than maps where position matters
Wormholes
Wormhole pairs are long-range connections between non-adjacent stars. A piece that activates a wormhole teleports to its pair. Wormholes create non-local strategic options. 6 Syn Wormholes.json is the only current map with wormhole edges.
Map design lever: wormhole pair distance and position define the teleportation advantage

The key insight for map design: the map determines which scoring strategies are viable, but the config vector determines which strategies are rewarded. A map with no HQ stars makes high hq_mult configurations irrelevant. A map with all stars clustered makes high dist_mult configurations low-reward. The mapmaker must design maps where the target mode's scoring strategy is genuinely viable.

Part II · Section 3 — Strategic patterns
Strategic Catalogue — What Each Map Should Do

Every map in the catalogue is a strategic intent, not just an aesthetic choice. When you ask the mapmaker for a map, you are asking it to create an environment where a specific cognitive challenge is the dominant experience. The map design follows from the strategic intent.

DISTANCE MAP Wide spread across canvas, stars placed near edges, long corridors, HQs at opposite corners SPT Spatial awareness, maximizing distance between held stars, resisting opponent's distance plays Central clustering, symmetric placement (makes spatial reasoning too simple)

Part II · Section 5 — Image input
Image → Map — Converting Visual Input to Strategic Space

The most powerful mapmaker input is an image: a photograph, a hand-drawn sketch, a real-world map, a geometric shape. The AI converts visual structure into game topology. This allows non-technical users to define spatial intent through drawing rather than coordinate specification.

What the image defines: the spatial distribution of territory, not the game mechanics. An image of a river delta defines: areas of density (where clusters will go), corridors (where connections will run), and open space (where stars will be sparse). The AI interprets the image as a spatial probability field, not a literal point-placement instruction.

Image input directive format: the human provides an image alongside a strategic directive. The AI extracts spatial structure from the image, then applies the strategic directive to determine which extracted elements become which game structures. Example: "use this image of the London Tube map as the topology, make it a CORRIDOR map for FRT mode with fixed HQs at Paddington and Canary Wharf."

The AI must not attempt pixel-perfect recreation of the image. It must interpret spatial intent and convert it to a playable game graph. The result should be inspired by the image, not a literal trace of it.

Part II · Section 6 — Information balance
Information Balance in Map Design

A map communicates information to players. How much information a map reveals — and at what cost — is itself a design dimension. Maps exist on a spectrum from fully legible (every strategic decision is obvious) to discovery-based (optimal strategy requires exploration and inference).

The system's goal (argmax E[KL]) benefits from discovery-based maps: when the student must figure out the map's strategic structure, their process of discovery is itself informative. A map where the optimal move is always obvious produces low information gain — the student's behavior reveals nothing about their cognitive model.

Map Legibility LevelWhat students immediately seeWhat requires discoveryInformation gain
TRANSPARENT
e.g. small symmetric 20-star grid		 All strategic structure visible from board state. Optimal moves are obvious on inspection. Nothing — execution is the only challenge. Low — behavior mostly reveals execution speed, not strategy formation.
LEGIBLE
e.g. Castle Conundrum		 General structure apparent. Major clusters and connections visible. Optimal chokepoint sequence, resource priority ordering. Medium — reveals whether student recognizes structure.
COMPLEX
e.g. CITYSCAPE		 Local neighborhood structure. Global structure not immediately apparent. Global map understanding, regional strategy, efficient path planning. High — reveals spatial reasoning, global-local integration.
DISCOVERY-BASED
e.g. LOTR ROSE		 Immediate neighbors only. Strategic structure must be built from experience. Map structure itself — the student must discover the topology as they play. Highest — every move is an information-gathering action about the map AND an attempt to score. The student's exploration strategy IS the signal.

Directive parameter for legibility: when requesting a map, the designer specifies legibility: "transparent" | "legible" | "complex" | "discovery". This controls star density, cluster size, degree distribution variance, and canvas utilization.
