The Challenge Compiler

Core distinction: A challenge is not a configuration. A configuration is the output of a challenge definition. The entropy engine selects a cognitive mode. The challenge meta-system selects a specific constraint within that mode, then resolves it to parameters, then generates a narrative. These are separate responsibilities.

Three Invariants

①

Cognitive Isolation

Each challenge targets exactly one cognitive variable. A challenge that simultaneously rewards territory AND HQ networks creates confounded signal — you cannot tell what the player learned. Each template has a single mode field. No exceptions.
②

Difficulty–Challenge Independence

Difficulty scales without changing the cognitive target. A SPATIAL challenge with 8 moves is harder than one with 20 moves — but it is still SPATIAL. Scaling the move count is a free axis. Scaling the distance multiplier changes the cognitive target — it is a locked axis. The resolver is only allowed to touch free axes.
③

Signal Purity

The challenge must generate interpretable behavioral data. If two different strategies produce identical behavioral signals, the challenge is underspecified. Every template explicitly declares which signals it generates and why those signals are valid under that template's constraints.

Similarity Spectrum

Pure entropy (maximally different every session) is pedagogically wrong. A player who barely lost needs a similar session to course-correct, not a completely different one. The spectrum determines how much the next session resembles the last. Mode coverage guarantee still holds over the 6-session window — but the system can repeat modes when the player is unresolved.

The "Barely Winning" Principle

The most informative session outcome is a close win — rank 50–75th percentile. This confirms: (1) challenge was appropriately calibrated, (2) player was genuinely engaged, (3) the session was competitive enough to generate clean signal.
too hard FLOW ZONE — maximum signal too easy
Landslide wins → system escalates challenge (RADICAL)
Consistent losses → system de-escalates (REMATCH)
Close games → system stays course or adjusts slightly (ECHO/PARALLEL)

The spectrum prevents the entropy engine from being either too random (pure chaos, no learning) or too consistent (same challenge every time, boredom). It operates on top of the 6-session Latin hypercube guarantee — spectrum position is the short-term signal; mode coverage is the long-term guarantee.

Loading Text Philosophy — Making the System Feel Alive

Never say: "Generating maximally entropic session..." — this is generic and breaks immersion.
Always say: something specific, observational, and slightly ominous. The system should feel like it has been watching.

Loading Sequence Structure

STEP 1: Context scan (500ms) "ANALYZING SESSION ${N} DATA..." "Scanning ${X} behavioral vectors..." STEP 2: Specific observation (600ms) [something specific to player history] e.g. "HQ network collapsed in round 3." e.g. "Steal rate 40% below session average." e.g. "No wormhole engagement in 4 sessions." STEP 3: Decision (400ms) "Mode selected: [MODE]" "Template: [TEMPLATE_NAME]" "Difficulty: [calibrated descriptor]" STEP 4: Overlay roll (optional, 300ms) "Applying INVERSION overlay..." (if rolled) "ITHKUIL numerals active." (if rolled) STEP 5: Codename reveal (dramatic pause, 800ms) [blank line] [SESSION N: CODENAME] STEP 6: Final line (200ms) [hint or ominous one-liner]
* The codename is the anchor. Players remember "the CHAIN REACTION session" — not the config. Session names create episodic memory of the learning journey. Each mode has its own name vocabulary so codenames signal mode without being explicit.

Game Plugin Interface — Extrapolation to Future Games

The meta-system core is game-agnostic. A future game plugs in by implementing this interface. The core never touches game-specific parameters. Game knowledge lives entirely in the plugin. Adding a new game = one plugin file. Zero changes to the meta-system core.
interface GamePlugin { // Identity id: string // "constellation", "centauri", etc. name: string // display name version: string // What can be configured configSchema: ParameterSpec[] // ParameterSpec { name, type, min, max, default, description } // Independent difficulty dimensions axes: DifficultyAxis[] // DifficultyAxis { // name: string // parameters: string[] // which configSchema params control this // min: any // easiest setting // max: any // hardest setting // modes: CognitiveMode[] // which modes this axis challenges // } // Which axes challenge which cognitive modes modeMap: Map<CognitiveMode, AxisWeights> // Atomic challenge templates templates: ChallengeTemplate[] // ChallengeTemplate { // id: string // mode: CognitiveMode // exactly one // name: string // constraints: ParameterOverride[] // cognitive constraint // free_axes: string[] // difficulty levers // locked_axes: string[] // must not change // success: SuccessCriterion // signals: SignalSpec[] // composable_with: TemplateID[] // incompatible_with: TemplateID[] // difficulty_at: (d: float) => ParameterOverride[] // narrative: string // } // Observable behavioral data signals: SignalSpec[] signalValidity: Map<Signal, CognitiveMode[]> // Runtime hooks validate(config): ValidationResult describe(template, config, player): string // player-facing outcome(sessionData): OutcomeRecord // OutcomeRecord { rank, percentile, signals, mode, template } }

The Plugin Test

A well-formed game plugin must satisfy: Can you specify ≥ 3 non-overlapping difficulty axes that each independently scale difficulty without changing the cognitive target? If yes: valid plugin. If difficulty and cognitive target are entangled in the game's design, the game needs redesign before it can plug in cleanly.
